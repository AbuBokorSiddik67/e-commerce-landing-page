# Security

This is a summary of implemented controls and known gaps, not an independent security audit or a claim that every route is protected. Production is blocked by the issues in [DEPLOYMENT.md](DEPLOYMENT.md).

## Controls in the current tree

- **Accounts and sessions:** bcrypt cost 12; random session tokens stored as hashes, with expiry and server-side revocation. New staff and staff password resets require a password change before dashboard/action access; selected media/export APIs also reject temporary-password sessions. Staff deactivation/reset revokes sessions and outstanding reset links. Server-side role validation rejects forged OWNER assignments and protects owner accounts from staff-management edits.
- **Passwords:** new/reset staff passwords require at least 10 characters and no more than 72 UTF-8 bytes; bootstrap owner requires at least 16 characters and at most 72 bytes. A reset token is hashed, one-use and expires after one hour; successful reset revokes other links and sessions. Session/link creation rechecks the account under a row lock against concurrent password resets and deactivation. Displaying a development reset link requires an explicit flag; never enable it on a network-accessible server or with real accounts.
- **Authorization:** permissions are checked in dashboard pages/actions and selected APIs; receipt/inspection requires order and inventory write access. Selected mocked and browser forgery checks passed, but the entire role/route matrix and alternative access paths have not been audited.
- **Secrets:** dashboard payment/courier credentials use AES-256-GCM; blank fields preserve ciphertext, and an incorrect key fails closed. Production key material must be at least 32 UTF-8 bytes. Courier claims bind the key and configuration; read the existing-installation/rotation warning in [DEPLOYMENT.md](DEPLOYMENT.md#credential-key-and-existing-installations).
- **Public data:** tracking uses a private capability and an explicit field allow-list; confirmation, tracking and reset page header rules request `no-referrer` and `private, no-store`. A development-mode reset response returned `no-referrer` and `no-store, must-revalidate`; verify the effective headers through the production proxy as Next.js can override cache directives. Order export prefixes potentially executable spreadsheet cells. Media upload requires `media.write`, checks size and file signatures, and uses generated keys.
- **Payment endpoints:** callback/IPN POST bodies are limited to 64 KiB and IPNs are rate limited. Unknown references and arbitrary unverified callback bodies/event IDs are not stored as webhook events; a known provider-verified reference gets at most one diagnostic event. The locked order/payment state, not the event row or browser redirect, determines payment. Exact amount/currency checks and real provider compatibility still require validation.
- **Headers/origin:** security headers and Content Security Policy are configured, with `X-Frame-Options` enabled except explicitly opted-in development previews. State-changing public requests with an `Origin` are checked against the request host; absent `Origin` is allowed for non-browser callers. Server Actions use Next.js origin handling. These controls depend on correct trusted-proxy configuration.

## Operational risks and remaining work

- Rate limits for login, reset, callbacks/IPN and other endpoints are **process-local**. The password-reset account key is IP-plus-email, not a global per-account limit. Restarts or multiple workers bypass shared enforcement. A trusted reverse proxy must overwrite rather than accept client-supplied `X-Forwarded-For`; deploy shared abuse protection before scaling or relying on it as a security boundary. Revoking a session does not cancel an already authorized in-flight action.
- CSP currently allows `'unsafe-inline'` and `'unsafe-eval'`; it is not a nonce-based strict policy. Third-party scripts and browser extensions with origin access can read browser-held checkout keys. Checkout keys and tracking/reset tokens are capabilities: do not log or share them. The bundled Nginx disables access logs, but other proxies, CDN, monitoring, application and browser logs must be reviewed separately.
- Recent notification/provider error handling avoids saving arbitrary SMTP/SMS error bodies and redacts provider-configuration audits. **Not all historical data is sanitized.** Payment attempts, courier shipment payloads/tracking evidence, notifications, customer records, older audit entries and backups may contain sensitive provider responses or personal data. Restrict access and review retention. Verified responses can be essential reconciliation evidence; do not blindly delete or rewrite them.
- Old and new writers cannot safely overlap: three real old-writer fixture assertions fail. An application lock alone does not fence old binaries or already accepted provider requests. Verify an independent cutover fence, drain, reconciliation and rollback procedure before any upgrade.
- Payment, courier, SMTP/SMS and S3 live behavior, production TLS, real backups/restores and official native Prisma execution are unverified. The latest full and production npm audits each reported four high Prisma/config-chain findings. Never automatically apply a major-version dependency fix without a migration and regression plan.
- Upload signature checks are not malware scanning. Provide appropriate storage isolation, access control, backups, quotas and scanning if the deployment requires them. Retention, account recovery, key storage/rotation and incident response are operator responsibilities.
