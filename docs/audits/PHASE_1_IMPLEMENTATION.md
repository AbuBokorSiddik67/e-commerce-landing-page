# LANDIQ Phase 1 implementation report

**Decision: FAIL — implementation is not yet verified or deployable.** The schema proposal is unexecuted, the native build cannot complete in this environment, real PostgreSQL concurrency has not been tested, and some provider recovery cases remain unresolved. Do not deploy or start Phase 2 on the strength of this report.

## Scope and assumptions

This work is for one active pre-production codebase and database. No old/new production overlap or cutover fence is a Phase 1 acceptance gate. Historical records may still be incomplete or inconsistent; they are not rewritten. Existing migration files and the three old-writer assertions remain unchanged.

## Implemented workflow

- Checkout retains product/order-item snapshots and the existing conditional sellable-stock decrement and movement. The 15-second same-customer/product duplicate check is repeated inside the transaction after locking the customer, including for different variants. This is **not** a durable checkout idempotency key: a retry after the window can still create another order.
- Order cancellation is recorded once under the order lock even after dispatch, while a courier claim is pending, or while payment needs reconciliation. The original internal note is preserved. Only a pre-dispatch order with consistent sale, delivery, balance, and payment evidence releases allocated stock automatically; otherwise no stock is credited. Payment, courier cancellation, and warehouse return remain separate.
- An authorized order writer can assign active staff to shop delivery, reassign with a snapshot check, and record dispatch, delivery, failure, return-in-transit, and returned events. Events remain physical history after commercial cancellation; they do not restore stock. Own delivery and third-party shipment assignment exclude each other under the order lock. An apparently assigned delivery with conflicting dispatch or courier evidence is left unchanged and flagged for review rather than recorded as safely unassigned.
- A return can contain multiple partial, idempotent physical receipts by order item. A receipt does not change stock. Authorized inspection posts its exact sellable/damaged split and corresponding movement(s) atomically in one transaction. Quantities are capped across all returns for an order item; previous unlinked/ambiguous stock movements fail closed. Completing a partial return leaves the order status unchanged, and a cancelled order stays cancelled.
- Third-party booking retains its durable local claim and runs provider I/O outside transactions. Staff can record a known booking using the original merchant reference, environment, account confirmation, and evidence; conflicting results stay under review. Courier cancellation has one durable operation per shipment and never automatically retries a pending/unknown write. If late evidence reverses a staff cancellation report, its prior local shipment status is restored only from an operation-bound snapshot and is labelled potentially stale; missing historical snapshots remain under review. A provider-reported or staff-reported cancellation is not proof of physical warehouse receipt. Tracking checks the original account/endpoint snapshot, stores only recognized status values, and does not write arbitrary provider echoes. Public tracking labels a booking as a provider record, not a verified provider update.
- Order detail, returns, and inventory dashboards expose these flows, the separate damaged balance, and movement buckets. New stock receipt/inspection actions require both `orders.write` and `inventory.write`; delivery and courier actions require `orders.write`.

## Schema / migration proposal

The intended additive model is in `prisma/schema.prisma`. The unexecuted SQL draft, additional checks, data impact, and review steps are in `docs/proposals/PHASE_1_ORDER_INVENTORY_MIGRATION.md`. It introduces `StockBucket`, `OwnDeliveryStatus`, `ProductVariant.damagedStock`, nullable cancellation metadata, item-level `ReturnReceipt`, `OwnDelivery`/`OwnDeliveryEvent`, `CourierOperation`, and receipt-linked movement uniqueness.

No migration, `db push`, reset, seed, historical data repair, real database operation, or live provider request was performed. Existing migrations were not edited. The app must not be run against the current database with this schema-dependent code until an independently reviewed migration is explicitly approved and applied. The proposed SQL and its extra checks have **not** been exercised against PostgreSQL.

## Exact unresolved criteria / blockers

1. **Runnable schema and real transactional integrity:** no approved migration or identity-verified, non-destructive PostgreSQL verification has occurred. In particular, simultaneous checkout, stock release, assignment/dispatch, return receipt/inspection, ledger constraints, rollback, and historical records need actual database tests. Conflicting historical shop-delivery assignments are flagged and blocked; this phase does not provide an automated correction workflow.
2. **Provider recovery and contract validation:** a known booking can be recorded by staff, but an unknown claim cannot safely be cleared as “not created” and retried: the current adapters do not establish authoritative provider absence or idempotency. Conflicting multiple parcel references also require investigation outside the automated flow. Pathao cancellation is only an adapter report, other listed adapters have no cancellation method, and none of the real provider endpoints/semantics were validated here. Claims remain blocked rather than risking duplicate shipments.
3. **Native build and browser verification:** official Prisma engine TLS failure prevents `npm run build`; no authenticated dashboard or checkout has been browser-tested against the proposed schema.
4. **Existing integration assertions:** the unchanged destructive-fixture suite is not compatible with the new schema or several explicitly changed workflow semantics. Its results, including the retained old-writer assertions, are unknown on this branch. Resolving the fixture and contradictory assertions requires user-approved test work; do not call the suite passing.
5. **Checkout retries:** the in-transaction customer lock is intended to serialize the existing time-window duplicate check, but there is no persistent checkout operation key. Lost responses retried after the time window can create another order, so durable checkout retry idempotency is not established.
6. **Other known payment and access limitations:** provider refund claims have no supported clearing workflow. Existing V1–V3 courier markers fail the V4 parser and have no automatic migration or recovery here. Booking responses may retain provider-supplied JSON, so provider echoes could include sensitive information. The earlier audit also identified customer confirmation pages that trust URL payment parameters and an unverified cancellation message, a dashboard redirect loop for some roles, and staff/media policy concerns; these were not fixed or comprehensively retested in this phase. See the historical audit for context, without treating its mixed-version gate as applicable to this deployment premise.

## Manual verification plan — not performed

After separately approving a reviewed migration and a non-destructive test plan, use only an identity-verified disposable PostgreSQL instance and mock providers:

1. Confirm read-only users cannot mutate orders, delivery, receipts, inspections, or courier records; verify that an order writer without inventory permission cannot receive/inspect stock.
2. Place concurrent same-customer checkouts (including different variants) and separate-customer checkouts; verify order counts, snapshots, sellable balances, and movements. Test last-unit competition and database rollback on a failed movement.
3. Assign/reassign an active staff member, dispatch, record failure/delivery/return, and cancel both before and after dispatch. Verify history, cancellation idempotency, and that no post-dispatch event by itself restores stock.
4. Receive multiple partial quantities, retry with the same operation key, reject over-receipt and mismatched inspection splits, and inspect sellable/damaged units. Verify both balances and receipt-linked ledger rows, concurrency, rollback, and partial versus full completion. Include ambiguous historical movements and cancelled orders.
5. With a mock courier, race booking against cancellation, inject timeouts and local write failures, verify no second external call, record known provider evidence, and verify a courier cancellation never credits inventory. Test late and conflicting results and account/environment changes.
6. Browser-check order, returns, and inventory screens with real permitted roles and historical data on that disposable instance. Separately obtain explicit authorization before any pre-production schema application, historical repair, or live-provider testing.
