# LANDIQ Phase 1 — final verification and closure

> **Historical snapshot:** The newer review added an additive migration and synthetic migration tests, but did not verify the official CLI or any existing installation. Three mixed-version writer safety assertions still fail; overlap during an actual upgrade or rollback is unsafe and must be independently fenced and reconciled. See [current deployment readiness](../DEPLOYMENT.md) and [testing](../TESTING.md) for the latest results.

## Decision: FAIL

**Phase 1 is not closed or deployable.** The new disposable PostgreSQL and browser checks passed within their stated scope, but the proposed migration has not been executed or checked against existing data, the native production build fails during the official Prisma engine download, and authoritative provider recovery remains unverified. Checkout idempotency is conditional on retaining a keyed operation; the old unkeyed API path is not durable. See the exact blockers below. Do not deploy or start Phase 2 on the strength of these results.

The scope is one active pre-production codebase and database. Hypothetical overlap between old and new production writers is not a current acceptance gate. Existing historical records must nevertheless be treated conservatively. Neither existing migration nor the historical safety assertions were changed. No pre-existing database, live courier, or live payment provider was contacted.

## Implementation and closure changes

- **Checkout:** an optional UUIDv4 operation key gives a checkout a deterministic, hashed order ID and a transactional HMAC fingerprint in its `ORDER_PLACED` audit record. A matching key and identical parsed checkout details replay the committed order beyond the old 15-second window. Different details or a missing/corrupt audit marker fail closed. Distinct keys mean distinct purchase intentions. A replay never repeats an online payment initialization while its outcome is in flight or unknown. Legacy callers without a key retain only the older time-window duplicate guard.
- **Checkout UI:** a browser-generated key and submitted flag are kept per product in `sessionStorage`, with no customer details in that storage entry. A lost response can be retried in the same tab after reload, including a multi-unit order whose stock is now zero. The shopper must re-enter the same details. Starting a different order requires explicit confirmation. Storage failure blocks submission rather than silently discarding the key.
- **Stock and returns:** `ProductVariant.stock` is sellable stock; `damagedStock` is separate. Receipt records physical custody without crediting stock. Inspection atomically posts the exact sellable/damaged split and receipt-linked movements. Partial receipts are capped across requests, and a cancelled order remains cancelled after physical return. A status retry now rechecks receipt and ledger evidence rather than accepting an ambiguous historical `RESTOCKED` or `COMPLETED` status. An unresolved financial refund is separate from a physically evidenced inspection; it is not treated as proof of either a refund or a return.
- **Cancellation and shop delivery:** cancellation is recorded once even when goods or payment require reconciliation; stock is released only with conservative pre-dispatch, sale and financial evidence. Shop delivery assignment, dispatch and physical events are serialized with cooperating order writers. A courier or shop-delivery return report is not a warehouse receipt.
- **Courier evidence:** a known booking or cancellation can be recorded as staff-reported evidence. A request-specific staff rejection report requires original-account/environment and rejection confirmations, but **does not clear the pending claim, allow a repeat booking, or release stock**. With successful local writes, a late contrary booking remains pending with both reports retained; additional distinct results are retained and displayed for investigation. Malformed rejection or conflict evidence also blocks resolution. If finalization fails and its fallback cannot safely write, pre-existing evidence is preserved and the claim stays blocked, but the late response may not be recorded and requires provider investigation. Provider responses, staff reports, manual entries, unknown outcomes and conflicts are labelled by provenance, not treated as independently verified physical facts.
- **Permissions:** receipt and inspection require both `orders.write` and `inventory.write`; courier and shop-delivery actions require `orders.write`. Read-only dashboard users no longer see stock adjustment, COD, refund, or internal-note mutation forms for which they lack permission. Server-side checks remain authoritative.

### Checkout capability and privacy limits

The browser uses `crypto.randomUUID()` (a random UUIDv4, 122 random bits) as a **secret capability**; a matching key plus checkout details can retrieve the order number and tracking token. The database stores a hash-derived ID and keyed fingerprint, not the raw key or customer details in the replay marker; ordinary order/customer records still contain personal data. Keep the key out of logs and untrusted scripts. An external API caller can supply a syntactically valid but predictable UUID, so randomness cannot be inferred from format alone. This is not a formal security review.

Retries require the same key and matching details. Tab closure, cleared session storage, another device, separate tabs or an explicitly new key are not automatically correlated; a copied tab may also copy session storage. Browser extensions or injected/third-party scripts with origin access can read it. Existing rate limits can temporarily reject repeated attempts. Audit retention or alteration can make replay require staff review. These limitations and optional-key legacy clients prevent an unconditional exactly-once checkout claim.

## Exact remaining blockers

1. **Migration and existing data:** no separately approved migration has been generated/applied or exercised as a migration on an identity-verified baseline with representative historical data. Actual database identity, migration state, existing inconsistent rows and CHECK compatibility remain unverified. Obtain a reviewed non-destructive plan and separate authorization before any real schema change or repair.
2. **Native production build:** official Prisma engine checksum download fails TLS in this environment. Restore trusted access to the official engine and run the normal native `prisma generate` and complete production build; the adapter-backed JS test client is not a substitute.
3. **Provider outcomes and recovery:** no live provider contract, account/environment identity, authoritative rejection/absence, cancellation, payment initialization or refund behavior was verified. Unknown claims never automatically retry or expire, and the staff-reported rejection does not clear them. There is no proven safe claim-clearing workflow for an authoritative no-booking result; multiple conflicting references still need investigation. If both booking finalization and safe fallback annotation fail, a late response may be absent locally even though prior evidence and the blocked claim are preserved. Pathao cancellation is only an adapter report, and some adapters do not support it. Provider-supplied JSON and staff evidence may contain sensitive echoes; no comprehensive redaction guarantee was established.
4. **Checkout scope:** unkeyed legacy API clients, loss of tab storage and separate purchase keys do not have durable deduplication. Real online payment checkout and provider-side idempotency were not browser-tested. The keyed tests do not establish global exactly-once ordering or protect a leaked/predictable key.
5. **Remaining browser and authorization coverage:** browser checks used synthetic COD and two roles on a development server. Eight selected direct viewer actions were rejected, but the order-writer-without-inventory case and other direct actions were only checked with mocks. Provider cancellation/refund, online payment, all roles/routes, historical data and the native production build remain unverified in a browser. Next development maps the tested forbidden server actions to HTTP 500 despite their internal 403 codes; production HTTP behavior is unknown.
6. **Historical suite and other known risks:** the old partial-schema/destructive helpers were not run or fully ported. Refund claims have no supported clearing workflow; V1–V3 courier markers fail closed under V4. Earlier audits identified payment adapter contract differences, potential provider/connection-result secret echoes, bKash token reuse after credential changes, customer confirmation trusting URL payment parameters, an unverified cancellation message, and dashboard/staff/media policy concerns. These were not comprehensively fixed or retested here.

## Reproducing the isolated checks

The test-only dependencies `@prisma/internals@6.19.3` and `@sparticuz/chromium@153.0.0` were installed without saving them to the lockfile. A Linux environment compatible with the packaged Chromium and embedded PostgreSQL is required. After `npm ci --ignore-scripts`, install them if needed with `npm install --no-save --ignore-scripts --no-audit --no-fund @prisma/internals@6.19.3 @sparticuz/chromium@153.0.0`. `LANDIQ_PHASE1_TEST_CLIENT=1 node tests/fixtures/generate-phase1-test-client.cjs` replaces the ignored `node_modules/.prisma/client` with an adapter-required **test** client; restore the ordinary native client with `prisma generate` before normal development or deployment. The generator never changes the tracked Prisma schema or contacts a database.

Run the opt-in database test with the invalid fallback URL above; it creates and verifies its own cluster. The static comparison is `python3 tests/fixtures/phase1-static-migration-compare.py`. For browser checks, start `tests/fixtures/phase1-browser-harness.cjs` with `LANDIQ_PHASE1_BROWSER_DISPOSABLE=1` and a new `LANDIQ_BROWSER_INFO_FILE` directly under ignored `tmp/` named `phase1-browser-*.json`; wait for Next to be ready. With those same variables, run `phase1-browser-smoke.cjs`, `phase1-browser-checkout.cjs` and `phase1-browser-fulfillment.cjs` in that order, then run `phase1-browser-postflight.cjs` after setting `LANDIQ_BROWSER_CLUSTER_DIRECTORY` to the harness-created cluster directory printed by that same process (the parent of its printed `data` directory). The postflight checks its process and database identity and opens a read-only connection. Use a **fresh harness for each repeated run** because the synthetic orders change. Gracefully stop the verified harness PID with `SIGUSR2` and confirm its metadata, cluster and processes are removed. Never substitute an existing server or database.
